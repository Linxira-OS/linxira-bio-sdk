# 把锁声明的解释器装回来之后：一次整窗重跑，与它改掉的一个结论

> Linxira Bio SDK 基准报告 · 2026-10-13。同一台机器、同一批种子输入、同一套脚本，唯一变化是解释器与其 pin 版本：Rust / Python / R 三后端在 8 项能力上各计时 10 次。原始报告、逐次读数、脚本与自标注都公开，可逐项复核。变更与声明见文末「版本与声明」。

> **数据状态**：八项能力的 N=10 测量于 2026-10-13 在空闲主机上完整跑完，未被打断。
> 阶段脚本、逐阶段环境门禁与 loadavg 记在窗口日志里；本窗首次在**锁声明的解释器**上运行
> （CPython 3.12 + 锁内 pin），门禁逐项核对为 match。归档已生成：两窗逐腿对照见第 5 节，
> 统计表与自举置信区间见 2026-10-13 归档的 `statistics.tsv`、`statistics-comparison.tsv`，
> 图形逐值校验为 986/986（中文）与 997/997（英文）。工具类对照臂见第 7 节，Python 腿的
> 隔离复测见第 6 节——两节引用的是本窗归档里的读数，不再是计划。

## 1. 摘要

我们在同一台低端 x86 机器（Intel Pentium Gold G7400，2 核 4 线程，15 GiB）上，把 2026-10-11 那批
八项能力的三语言测量**整窗重跑了一遍**。重跑的原因不是机器变更，而是一句我们此前说得不够清楚的话：
"这批数字跑在锁定环境里"。核对时发现，锁文件头部写着 `Runtime: CPython 3.12`，CI 也按 3.12 安装它，
而测量主机跑的是 **CPython 3.14.7**；更要紧的是，锁里那两个 pin 在 3.14 上**根本装不成**。

结果按两段式预注册规则与前一窗口逐腿对齐后是：

- **Rust 腿与 R 腿在两套环境间几乎不动**：八项能力的 Rust 中位数差异 ≤0.7%（最大 0.64%），
  R 腿 ≤1.3%（最大 1.23%），多数组落在噪声带内——同一份代码、同一份输入，两个窗口的机器状态可复现。
- **Python 腿是唯一对解释器与 pin 版本敏感的臂**：两窗差异从 **−19.0% 到 +123.6%**（八项能力），
  方向不一致，因此不能用一个系数概括。
- 由此**改掉一个结论**：`sequence.stats` 的 Python 腿在锁声明的环境里是 **1845 ms**（上一批为 825 ms），
  对 Rust 810 ms 的比值从 **1.02× 变为 2.2778**（自举置信区间 **2.2716–2.3210**，噪声带 0.0551，
  判定 **material**），**远超预注册的 1.10 阈值**；前一篇报告里"可分辨但不构成实质差距"的判定
  在**我们实际发布与 CI 使用的那个环境里**不再成立。第 6 节的隔离复测进一步说明：改掉这一结论的
  是解释器代际，不是锁里的包版本。
- **内存侧的结论不受影响**：Rust 峰值 RSS 仍为 Python 的 1/2.2–1/10.8、R 的 1/5.5–1/54.7（本窗实测区间）。

需要强调的边界：本窗**没有**改变算法、输入或协议，只把解释器换成锁声明的那一个。因此这一篇
不是"新基准"，而是**同一基准在正确环境下的一次复算**，以及由此暴露出的"环境必须随数字一起公布"
这一具体代价。

## 2. 起因：锁和主机差了两代解释器

上一批数字的解释器环境是 CPython 3.14.7，而它用的库版本是 `biopython 1.88 / numpy 2.5.4`，锁 pin 的
却是 `1.85 / 2.2.4`。这两个库版本**并不在归档报告里**——报告的环境块只记录了解释器（`Python 3.14.7`）
与 R 版本；库版本写在当时的环境说明与前一篇正文中。（也就是说：读者无法仅凭归档复核这两个库的版本，
这本身是环境记录的一个缺口，已登记为待补。）最初的记录把它写成"环境与锁不一致"，并在复现文档里
列为待修项。真正动手修的时候，证据指向另一个解释：

- 锁文件头部写着 `Runtime: CPython 3.12`；CI 的安装步骤用的也是 3.12。
- 测量主机上只有 `/usr/bin/python3.14`，没有 3.12。
- 在 3.14 上执行 `pip download --only-binary=:all: biopython==1.85`，回答是
  `from versions: 1.86, 1.87, 1.88`；`numpy==2.2.4` 回答 `from versions: 2.3.2, …`；
  1.85 的源码构建亦失败（C 头文件报错）。

也就是说：**那两个 pin 在 3.14 上不存在可安装的轮子**，上一批的 `1.88 / 2.5.4` 并不是"装错了"，
而是 Python 3.14 当时唯一能装到的版本。真正的错误是**让锁与主机差了两代解释器**，再把结果描述成
"环境没有对齐"。这条更正连同可复现的命令记在更正台账里（
[corrections-log.md](https://github.com/Linxira-OS/linxira-bio-sdk/blob/main/docs/outreach/corrections-log.md)）。

## 3. 重跑改了什么

改的不是算法，而是让"锁定环境"这句话可以被**证明**，而不只是被声明：

1. **装回锁声明的解释器**：用 `uv` 在用户目录安装 CPython 3.12（不动系统包），
   再用 `uv pip install --require-hashes -r <lock>` 把锁装进它建的虚拟环境。
2. **门禁先过再测**：既有的锁/环境门禁脚本（[verify-lock-env.py](https://github.com/Linxira-OS/linxira-bio-sdk/blob/main/scripts/benchmark/analysis/verify-lock-env.py)）在测量前逐项比对 lock 与已安装发行版，
   本窗四项（biopython / numpy / pyfastx / pytrf）全部 `match`，任一项不符则各阶段脚本拒绝测量。
3. **每个数字自带代码标签**：构建期把分支、提交与 `git describe --tags --always --dirty` 烘进二进制，
   报告的环境块三项齐全；窗口另写 `code-label.txt` 记录分支、完整提交、describe、工作树是否干净、
   锁的 sha256 与实际解释器版本。因为本项目**尚未发布任何 release**，`describe` 输出的是短提交号
   （本窗 `f3b9f17`），标签本身即说明了发布状态。
4. **无人值守时不允许"假装完成"**：任一阶段失败会以 `RUN-WINDOW-INCOMPLETE` 结束并点名阶段，
   而不是留下一个空归档冒充结果。
5. **开跑前的空闲判据**：除"无 CI 作业"外，新增"无 >5% CPU 进程且无 aria2c"，
   并要求连续多次采样都为空闲（本窗因维护者明确要求尽快开跑，把连续采样数降为 1）。

提交痕迹：标签机制 [`58b744a`](https://github.com/Linxira-OS/linxira-bio-sdk/commit/58b744a)（分支/提交/describe 烘入报告）、
解释器更正与文档 [`60f2bb1`](https://github.com/Linxira-OS/linxira-bio-sdk/commit/60f2bb1)、
阶段失败标记 [`6c0c279`](https://github.com/Linxira-OS/linxira-bio-sdk/commit/6c0c279)、
空闲判据 [`f3b9f17`](https://github.com/Linxira-OS/linxira-bio-sdk/commit/f3b9f17)。

## 4. 数据与方法

- **机器与整窗条件**：同前一批；`powersave` 调节器全程不变；输入在 tmpfs 上，避免磁盘延迟进入测量；
  串行执行，测量期间不跑编译、Lint、归档或任何非测量作业。逐阶段 loadavg 与作业计数见窗口日志。
- **输入**：与前一批**同种子、同尺寸**生成（`big.fa` 101,667,131 B、`reads200.fq` 217,217,047 B——两者都是窗口日志里输入生成行记录的尺寸），
  生成的摘要随归档给出，可按 sha256 复核。
- **协议**：每项能力、每后端各 1 次不计时预热 + **10 次计时**；后端顺序固定 `rust→python→r`，
  因此跨后端的频率/热漂移是已知局限。
- **披露（本窗特有）**：维护者在同一台主机上有跨夜的数据作业。为不发布"有争用的窗口"，
  本窗在开跑前等待其下载与校验结束，并在最后一项测量（SSR 的 R 腿）期间保持主机空闲；
  测量进程在其作业开始前已全部退出（让机由守卫脚本完成，其日志与窗口日志一并归档）。
  为排除尾部重叠对读数的影响，第 5 节给出 SSR 逐次读数与末次离群检验。
- **日志能证到什么、证不到什么**：窗口日志记录了预检（CI 作业计数、空闲判据）、空闲等待的逐次采样，
  以及各阶段的 start/ok 行；它**没有**驱动器的收尾行——最后一项测量落盘后，让机守卫先停掉了驱动器，
  所以 `RUN-WINDOW-DONE` 从未打印。SSR 是否真正完成由报告自身证明（10 次计时与逐次读数，见第 5 节），
  而不是由日志的这一行证明。写在正文里，免得读者以为日志被漏掉了。

同样为 material。（数字出自本窗归档的 `statistics.tsv`，不是本文手算。）

## 6. Python 腿的环境敏感性：把解释器与包版本分开

第 5 节留下一个必须回答的问题：Python 腿在两窗间动 −19.0% 到 +123.6%，方向还不一致。而同一时间变了
两件事——解释器（3.14.7 → 3.12.15）与两个包（biopython 1.88 → 1.85、numpy 2.5.4 → 2.2.4），
无法把差异归给其中任何一项。我们做了三格隔离复测：同一脚本、同一份输入、同一台机器、同一天，
每格各 10 次，只动这两层。表 2：

| 格 | 解释器 | biopython / numpy | sequence.stats | expression.pca |
| --- | --- | --- | ---: | ---: |
| A | CPython 3.12.15 | 1.85 / 2.2.4（锁内） | 1840 ms | 3250 ms |
| B | CPython 3.12.15 | 1.88 / 2.5.4（前窗那套） | 1840 ms | 3235 ms |
| C | CPython 3.14.7 | 1.88 / 2.5.4（前窗那套） | **820 ms** | **3985 ms** |

三行读法：

1. **A 与 B 一致**（1840 vs 1840、3250 vs 3235，都在噪声内）⇒ **包版本不是变量**：把 biopython 与
   numpy 换成锁里的那两个版本，Python 腿一点不动。
2. **B 与 C 差得很大，而且方向不一致**：换到 3.14 后 `sequence.stats` 快 **2.24×**（1840→820），
   `expression.pca` 慢 **1.23×**（3235→3985）⇒ **变量是解释器代际**，而它对本项目 Python 臂的影响
   不是"新解释器更快"，而是"逐能力不同方向"。
3. **C 复现了前一窗的 Python 腿**：前窗 825 ms / 4010 ms，C 是 820 ms / 3985 ms（各 −0.6%）⇒
   第 5 节那张表的 Python 列，是**环境差，不是机器差**，也不是我们的代码在两次测量之间变了。

计划中的第四格（3.14 + 锁内 pin）**不存在**：那两个 pin 在 3.14 上没有可安装的轮子（第 2 节）。
缺失本身就是事实，因此这里不补一个假格子。

**口径**：表 2 是 Python 腿的对照性测量，与表 1 不是同一批，**不进 `summary.json`**，只作为本窗归档的
`env-isolation/` 单独存放（含每格的十次原始读数与逐格 loadavg）。它回答的是"环境记录为什么必须随数字
公布"，而不是替代任何一项能力的正式读数。

**仍未定的一件事**：解释器为什么在 `sequence.stats` 上带来 2.24× 的杠杆——是某条 C 扩展路径的构建差异，
还是 3.14 上解析路径本身的变化——**我们没有证据**，因此不猜；这一条已登记为待办。

## 7. 工具类对照臂（第二类臂）

生态工具臂（`arm_class=tool`）测量的是"用户真会调用的那个命令"，与三语言一致性臂（parity）是两类：
**报告里不存跨类比值**（`speedup`/`memory_saving` 恒为 null），两类臂也不同表、不同图。
注册表里四个工具，本窗四个都跑成了。第四条一开始被**静默跳过**：`tool-arms.sh` 把锁定 venv 放在
`PATH` 最前，注册表的版本探测（`python3 -c "import sklearn"`）因此落到一个没装它的解释器上，
runner 就直接少产出一份报告——包一直在主机上（2026-10-12 那轮就是在这台机器上量的
scikit-learn 1.9.1），它在 3.14 那套环境里；补测用那个解释器跑，环境记在报告里。这个失败模式
本身记成了待办（要加一道"注册表四个 id、归档四份报告"的门禁）。表 3：

| 工具 | 版本 | 能力 | 中位数（N=10） | 峰值 RSS |
| --- | --- | --- | ---: | ---: |
| `pyfastx stat` | 2.3.1 | `sequence.stats.v1` | 10.0 ms | 15.2 MB |
| `seqkit stats` | v2.14.0 | `sequence.stats.v1` | 30.0 ms | 26.9 MB |
| R `prcomp` | 4.6.1 | `expression.pca.v1` | 120.0 ms | 79.0 MB |
| scikit-learn `PCA` | 1.9.1 | `expression.pca.v1` | 700.0 ms | 139.3 MB |

对我们的对应臂（同输入、同机器）：`pyfastx stat` / `seqkit stats` 分别是我们 Rust 臂 810 ms 的
**81×** 与 **27×**；R `prcomp` 是我们手写 R 臂 2745 ms 的 **23×**；scikit-learn `PCA` 是我们手写
Python 臂 3250 ms 的 **4.6×**。**这些比值只出现在这句散文里，不进任何表格、不进任何图**——
两类臂的数字回答不同的问题（规则见本仓库路线图 §7.1）；表 3 因此只列工具侧事实。

**输入身份**：本窗起，工具臂报告自带被测输入的 path / bytes / sha256。`big.fa` 在报告里是
101,667,131 B、sha256 `9f8a4cb4…044e78`，与同窗归档的 `inputs.sha256` 逐字节一致——工具臂与
一致性臂量的是同一份文件，而不是"看起来差不多的一份"。

三条限制，写在这里是因为这些数字容易被读得比它们能支持的更多：

1. **计时器是量化的**：工具臂用 GNU `time -v`，报的是百分之一秒，因此每个臂的十次读数在 10 ms 这一
   位上完全相同（IQR 0.000 ms、CV 0.00%）。一致性臂用的是引擎自己的毫秒计时器，这也是两类臂只能以
   **标注了类别的散文**比较、从不并表的一个具体原因。
2. **不是同一个任务**：我们这一侧输出 11 列（含 `au_n`、`gc_percent`、`n_count`/`n_percent`）；
   `seqkit stats` 的默认输出是 8 列（file/format/type/num_seqs/sum_len/min_len/avg_len/max_len，
   我们在 v2.14.0 上实跑核对过），`pyfastx stat` 读的是它自己预建的索引（`/tmp/lxn13/big.fa.fxi`，
   28,672 B）。要写"这项作业该用哪个实现"，前提是**同一个输出集合**上有一条对拍；这条测量还没做
   （见 §7.1）。
3. **同一个工具在两轮里读数不同**：2026-10-12 那轮记录 `pyfastx stat` 为 **30.0 ms**，本窗记录
   **10.0 ms**（同一台机器、同一份 `big.fa`）。两份归档各自对自己的那次会话成立，**差异尚无解释**；
   因此前一篇用的"27×"与本篇的"81×"是两个会话的两个数，不是谁更正谁。

本窗新增的 **seqkit** 是最接近"同一件事"的一条臂：它回答"是流式读一遍 FASTA 本身就贵，还是我们的
记录式解析贵"。它 30.0 ms、我们 810 ms——但按第 2 条限制，这个倍数只能作为散文陈述，不进表、不进图。

### 7.1 为什么表里会出现"比 Rust 还快"的数字

读者应当在这里停下来问一句：`pyfastx stat` 30.0 ms 比我们自己的 Rust 臂 810 ms 快 27 倍，
那这篇报告里的"Rust 快"是怎么成立的？答案不是修辞，而是三个方向不同的对照：

**（一）工具比我们的 Rust 快——确实存在，差距要照实说，但也不能当成"同一件事的胜负"。**
`sequence.stats` 我们这一侧输出 11 列，其中三项不是"顺带计数"能得到的：`au_n` 是 Nx 曲线下面积，
需要**完整的长度分布**；`gc_percent` 需要**逐碱基分类**（只把 A/C/G/T 计入分母）；`n_count`/`n_percent`
需要识别 N。工具的默认输出不含这三项（`seqkit stats` 的 8 列里没有 GC%、N50 或 N 计数，在 v2.14.0 上
实跑核对；`pyfastx stat` 则是对它自己预建的 `.fxi` 索引做读）。**两侧的输出集合并不相同，因此这不是
同一任务的对拍。**

但差距也不能用"输出集合不同"一句话带过。本窗读数是 `pyfastx stat` **10.0 ms**、我们 **810 ms**
（同一份 101,667,131 B 的 `big.fa`，N=10，两侧都记录输入身份）：按这一档位换算，工具侧至少是
**10 GB/s**，我们侧约 **125 MB/s**（101,667,131 B ÷ 0.810 s）。差距不在 I/O——输入在 tmpfs 上、
页缓存是热的——而在我们的记录级开销（逐条构造、累计与排序）与逐碱基扫描。另需说明：那个 10 ms 是
计时器的一个档位，工具侧真实用时在 5–10 ms 之间，所以这个倍数只能读作"≥81×"。

**这条差异不是需要辩解的缺陷，而是一个可用的结论**。本项目的定位是：**大多数算法我们用 Rust 加速；
同样的活如果现成的实现已经更快，就用现成的那个，而不是重新写一遍**（README 的 "On Rust" 一节）。
所以"某个工具比我们的 Rust 臂快"的处理方式是两步：① 把两边的数字都记下来（本节与第 7 节）；
② 让**选路成为就那项作业写下的判断**——基准在这里的作用是让两边数字都可核，而不是替谁决定，
也不是声称某一方处处都赢。要写下这样的判断，前提是**同一个输出集合**上有一条对拍：例如让工具也只
输出我们那几列（`au_n`、`gc_percent`、`n_count`），或让 `pyfastx` 关掉预建的 `.fxi` 索引再比。
**这条测量我们还没做**，所以本节与表 3 的倍数只作记录，不作替换依据。profile 我们自己的
`sequence.stats`（把 810 ms 拆成读、构造、统计三段）的价值正在于此——它告诉我们分界在哪里，
从而决定哪些工作继续由我们的实现承担、哪些交给生态工具。任何实现改动都会改变数字，因此要另开一个
测量窗口，而不是悄悄换掉已有读数。

**（二）工具比我们的"手写对照臂"快——这是设计使然，不是意外。**
一致性臂（parity）是**手写**实现，存在的目的是隔离运行时：R 臂用自己写的幂迭代算 PCA（2770 ms），
Python 臂用自己写的实现（4010 ms）；而用户真正会调用的是 `stats::prcomp`（150.0 ms）与
scikit-learn `PCA`（725.0 ms）。这条差距衡量的是**"手写 vs 惯用库"**，不是"R 语言 vs Rust 语言"。

**（三）我们的 Rust 比两边都快——在这一项上成立（也正是"用 Rust 加速"该出现的场合），但同样要标口径。**
同一个 PCA 任务，我们的 Rust 臂是 20 ms：对上本窗读到的 `prcomp` 120.0 ms 是 **6×**，对上本窗读到的
scikit-learn `PCA` 700.0 ms 是 **35×**（2026-10-12 那轮这两个工具分别是 150.0 ms 与 725.0 ms，对应
7.5× 与 36×——两轮各自对自己那批读数成立，不互相更正）。
与（一）一样，这里也不该让读者以为是严格同口径：那次对照的记录里写明 `prcomp` 返回 40 个主成分、
scikit-learn 返回 39 个，两个臂的实现也不相同——**这两个倍数是标注了类别的散文，不是同口径的表格数字**。
所以"Rust 快"这个说法在本报告里**只对一致性对照成立**，而且每一项都按预注册规则逐一给结论，
不靠一个总印象。

**正因为这三个方向混在一起会被误读，两类臂才有硬性隔离**：工具臂的报告里**不存**跨类比值
（`speedup`/`memory_saving` 恒为 null），两类臂不进同一张表、不进同一张图（规则见仓库路线图的
§7.1），跨类比较只允许像本节这样**标注了类别与工作量的散文**。

## 8. 这台机器是否普通

外部锚点用于回答"这台低端机是否处于正常档位"。在同一主机上测得：zstd 1.5.7 `-1` 242 MB/s、
`-19` 1.13 MB/s（峰值 RSS 199 MB）、解压约 1070 MB/s；对照 zstd 官方 README 表（i7-9700K，
Silesia 语料）为 0.47× 与 0.69×。`openssl speed sha256` 8 KiB 为 1748 MB/s（未与公开表比较：OpenSSL 没有发布覆盖本口径的基准表，
这也是锚点记录里给出的理由）。lzbench 由源码构建并独立复现了 zstd `-1` = 242 MB/s 这一读数。

**限制**：Silesia 语料在本网络不可得（实测镜像 32 KB/60 s 且部分文件会重置），因此
**没有做任何与公开压缩数字的同类比较**；这一条作为方法学限制写明，而不是隐去。

## 9. 失败先讲

按发生的顺序：

1. **发布 CDN 不稳定**：两个网络下下载发布物出现截断（7.6/8.8 MB）、0 字节与重定向到错误页；
   可靠路径最终是 git-over-https、包管理器，以及**用发布方 API 的 asset digest 校验**。
2. **`fastp` 没有官方二进制资产**：主机上那个看似"已下载"的 `fastp` 其实是一个 9 字节的
   `Not Found` 页面。这条也是"工具供给"设计里"不要假装总有 URL"的直接来源。
3. **解释器错配**（第 2 节）：锁声明 3.12、主机跑 3.14，pin 在 3.14 上不可安装。
4. **主机是共享的**：维护者的跨夜数据作业与本窗争用同一台机器。处理方式是等待 + 空闲判据，
   并在测量结束后立即让机；尾部重叠用逐次读数检验（第 5 节）。这一条改变的是**流程**：
   窗口不再是"想跑就跑"，而是"先证明机器空闲，再开跑"。
